# Step 8: 発展課題

> **本書の対応箇所**:『Rustで始めるTCP自作入門』3.10「総まとめ・ファイルアップロード」、第4章「振り返り編」(4.1 高速再転送、4.2 パフォーマンス、4.3 TCPの欠陥・そしてQUICへ)。本書との対応: A-3 = 4.1、C-3 = 3.10 の複数クライアント対応、E = 3.10 のファイルアップロード

ここまでの実装は「動く最小限」です。本物のTCPとの差を埋めていく課題を、取り組みやすい順に並べます。それぞれ、どこを変えるか・何で確認するかを添えています。

## A. 信頼性まわり

### A-1. 順序入れ替わりのバッファ(難易度: 低)

今は `seg.seq > rcv_nxt` のセグメントを捨てています。これを `{seq: payload}` の辞書に取っておき、`rcv_nxt` が追いついたら連結して取り込むようにします。

- 変える場所:`_handle_other()` のデータ処理
- 確認:`--loss-in 0.3` で大きなデータを受信し、再送されるセグメントの数が減ること

### A-2. RTTの計測とRTOの計算(難易度: 中)

セグメントを送った時刻と、そのACKが返った時刻の差がRTTです。RFC 6298 の式で更新します。

```
最初のRTT測定:  SRTT = R,  RTTVAR = R/2
以降:           RTTVAR = 3/4·RTTVAR + 1/4·|SRTT − R|
                SRTT   = 7/8·SRTT   + 1/8·R
RTO = SRTT + max(G, 4·RTTVAR)     (G はクロックの粒度。下限1秒が推奨だがLinuxは200ms)
```

注意:**再送したセグメントのACKからはRTTを測らない**(Karnのアルゴリズム)。どちらの送信に対するACKか分からないからです。

- 変える場所:`RtxEntry` に送信時刻はあるので、`_ack_received()` で計算
- 確認:`ss -ti` でカーネル側の `rto:` と比べる

### A-3. 高速再送(難易度: 中)

同じ ack 値が3回続けて届いたら(重複ACK)、その ack から始まるセグメントをタイムアウトを待たずに再送します。

- 変える場所:`_handle_other()` で `seg.ack == snd_una` のときカウント
- 確認:`--loss 0.3` で大きなデータを送り、`RTO経過` より先に再送が起きること

### A-4. 再送のときの送信(難易度: 低)

今は `_check_retransmit()` が先頭だけを再送します。先頭を再送したあとに後続もタイムアウトしていたら、まとめて再送すべきかどうか、RFCを読んで判断してください(RFC 6298 5.4〜5.7)。

## B. フロー制御・性能

### B-1. ゼロウィンドウプローブ(難易度: 低)

相手のウィンドウが0のとき、今の `send()` は相手からのウィンドウ更新を待つだけです。更新の通知が落ちたら永久に待ちます。定期的に1バイトのセグメントを送って、ウィンドウを問い合わせる仕組みを足してください。

- 確認:`rcv_wnd` を小さくしたエコーサーバーに、大きなデータを送る

### B-2. 遅延ACK(難易度: 低)

今はデータを受け取るたびに即ACKを返しています。少し待って、返事のデータに相乗りさせる(piggyback)か、2セグメントに1回ACKするようにするとパケット数が減ります。スニファで数えて比べてください。

### B-3. Nagleアルゴリズム(難易度: 低)

小さなデータを連続して `send()` すると、今は1つずつセグメントになります。「未ACKのデータがあるあいだは、小さなデータをためて1つにまとめる」のがNagleです。対話的なアプリでは遅延の原因になるので、`TCP_NODELAY` で切られることが多い、という背景も一緒に調べてください。

### B-4. 輻輳制御(難易度: 高)

ここまでのTCPは「相手のバッファ」しか気にしていません。「ネットワーク」の混み具合を見て送る量を絞るのが輻輳制御です。

最小限の実装(RFC 5681):

```
cwnd(輻輳ウィンドウ)を持つ。送っていい量 = min(snd_wnd, cwnd)
スロースタート:   ACKが返るたびに cwnd += MSS     (RTTごとに倍になる)
輻輳回避:         cwnd >= ssthresh になったら、RTTごとに cwnd += MSS
ロス(タイムアウト): ssthresh = cwnd/2, cwnd = MSS に戻す
```

- 確認:`--loss 0.05` で大きなデータを送り、`cwnd` の推移をログに出してグラフにする。のこぎり型になれば成功
- その先:Linuxの既定であるCUBIC、GoogleのBBRが何を変えたのかを調べる

## C. 堅牢性

### C-1. RSTを送る(難易度: 低)

今は不正なセグメント(LISTENへのACK、閉じた接続へのデータなど)を黙って捨てています。RFC 9293 3.5.2 に従ってRSTを返すようにします。ただし、**ラボ環境では host1 の RST を iptables で捨てている**ので、確認にはその設定を外す必要があります(`lab/setup_inside.sh`)。外すとカーネルのRSTも通るようになり、自作TCPの接続が壊されます。カーネルが反応しないよう、自作側で使うポートを `net.ipv4.ip_local_reserved_ports` などで避ける工夫が必要です。

### C-2. シーケンス番号の周回(難易度: 低)

seqは32ビットで、4GBほど送ると0に戻ります。`snd_una < ack <= snd_nxt` のような比較は、周回をまたぐと壊れます。差を32ビット符号付きとして解釈する比較関数を作り、すべての比較を置き換えてください。

```python
def seq_lt(a, b):   # a < b (mod 2^32)
    return ((a - b) & 0xFFFFFFFF) > 0x7FFFFFFF
```

- 確認:`iss` を `2**32 - 10` 固定にして、20バイト送る

### C-3. 複数接続(難易度: 中)

LISTENソケットと接続済みソケットを分け、SYNが来るたびに新しい `Connection` を作り、完了したものをキューに積んで `accept()` で取り出す形にします。rawソケットを1つにして、4つ組で振り分ける「ディスパッチャ」が必要になります。

- 確認:ncを2つ同時につないでエコーする

### C-4. キープアライブ(難易度: 低)

Step 3 で見たように、相手のプロセスが消えても接続は残ります。一定時間無通信なら「seq = snd_una − 1」の空セグメントを送り、ACKが返るか確かめる仕組みを足してください。

## D. 仕上げ

### D-1. 本物と比べる

ラボの外(普段のWSL)で、本物の `tcpdump` と `ss -ti` を使って、カーネルのTCPの挙動を眺めてください。`ss -ti` には cwnd、rto、rtt、再送回数など、この教材で作った変数がそのまま出てきます。

```bash
sudo tcpdump -i any -nn port 443 &
curl -s https://example.com > /dev/null
ss -ti dst example.com
```

### D-2. 別の言語に移植する

同じものをRustやGoで書き直すと、1回目で曖昧だった部分(バッファの境界、周回、状態遷移の抜け)がすべてあぶり出されます。Rustの参考実装として `teru01/toytcp`(GitHub)があり、この教材と同じくrawソケット+netnsの構成です。ただしスレッド+ロックの設計なので、この教材の単一ループ設計と比べてみると、どちらの難しさがTCP由来でどちらが言語由来かが分かります。

### D-3. 原典を読む

ここまで来れば、RFCが読めます。

- **RFC 9293** — TCPの現行仕様(2022年にRFC 793などをまとめ直したもの)。3.10 "Event Processing" が、この教材の `_handle_*` に相当します
- **RFC 5681** — 輻輳制御
- **RFC 6298** — 再送タイマー
- **RFC 7323** — ウィンドウスケール、タイムスタンプ(本物の tcpdump で `options [... wscale 10, TS val ...]` と出るのはこれ)

## E. アプリケーション(本書 3.10「総まとめ・ファイルアップロード」)

### E-1. ファイルアップロード(難易度: 中)

本書が最後に作るアプリです。クライアントが数MBのファイルを読み込んで `send()` し、サーバーが受け取った内容をファイルに保存します。データが MSS の何千倍もあるので、ウィンドウいっぱいまで送って ACK を待つ、という動きが本格的に起きます。

- 作るもの:`steps/fileclient.py <port> <ファイル>`、`steps/fileserver.py <port> <保存先>`(サーバーは `recv()` が `b""` を返すまで書き続ける)
- 確認:`lab/lab.sh loss 1%` を入れた状態で数MBを送り、`md5sum` が一致すること。かかった時間も測る
- その先:A-1(順序入れ替わりのバッファ)と A-3(高速再送)を入れると、ロスがあるときの転送時間がどれだけ縮むかを比べる

### E-2. 複数クライアント(難易度: 中)

本書のエコーサーバーは、接続ごとにスレッドを立てて複数のクライアントを同時に相手にします。この教材の単一ループ設計でこれをやるには、C-3(複数接続)を先に実装して、ループの中で全接続を順番に `_step()` する形にします。

- 確認:`lab/lab.sh exec host2 nc 10.0.0.1 9000` を2つ同時につないで、どちらもエコーが返ること
